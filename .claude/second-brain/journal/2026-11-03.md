# 2026-11-03

- Set up the repository: CLAUDE.md, `.editorconfig`, `.gitattributes`, `.gitignore` and this second
  brain, taken over from RcinelTranslate (which took them from MyMonoRepo).
- The owner moved to one repository per application ([[0001-one-repository-per-application]]).
- Copied what LaunchHeim learnt about Valheim and BepInEx into [[valheim-modding]], and the owner's
  release habits plus what is known about Thunderstore into [[thunderstore-publishing]].
- Wrote down the owner's feature description and the open design questions in [[rcinellevel]]. The
  biggest one: what "neutral point" means.
- On the machine: Valheim in `/mnt/games/SteamLibrary`, Unity 6000.0.75f1, the LaunchHeim `test`
  instance. Seen there: MultiUserChest's Jotunn dependency isn't installed.
- The owner decided: the neutral point is the cut-and-fill balance
  ([[0002-neutral-point-is-cut-and-fill-balance]]), the tools are new items
  ([[0003-separate-tools]]), and the mod uses Jotunn ([[0004-jotunn]]).
- `main` started as an empty root commit pushed by Claude, at the owner's choice, so the setup
  could go through a PR like every other change.

Second session (after PR #1 was merged):
- Read the terrain and network code ([[terrain-and-multiplayer]]): edits go to the terrain's owner as
  a prefab hash, so everyone needs the mod ([[0005-everyone-needs-the-mod]]); vertices are 1 m apart
  and level ops can't rotate, so walls are as steep as one cell allows and run along the world axes.
- The owner decided: the player sets the area ([[0006-probe-area-set-by-player]]), the recipes
  ([[0007-recipes]]), `Rcinel.Level.*` ([[0008-rcinel-level-namespace]]), Blender models loaded at
  runtime ([[0009-blender-models-loaded-at-runtime]]), and releasing as CodeIsNotEvil on Thunderstore.
- Icons: `scripts/text_logo.py` and Kode Mono copied from MyMonoRepo; RL logo, probe and level hoe
  SVGs, PNGs rendered from them, `package/icon.png`. The hoe took four tries before it stopped
  reading as a hockey stick, an arrow and a checkmark: drawing it upright and rotating the group
  keeps blade and handle square to each other.
- Blender isn't installed yet; the owner installs it (`sudo pacman -S blender`).

Third session:
- The owner settled the frame: circle, square or rectangle, scroll to resize, the rectangle only
  toward where the player looks; height also by hand ([[0010-area-shapes-and-scroll]]). Claude read
  "the direction the user looks in" as "the edge on that side moves"; to confirm in the game.
- Blender 5.2.3 installed by the owner. `models/build.py` makes the probe and the level hoe
  ([[0011-model-designs]]), exports OBJ plus a numpy-drawn atlas, and renders Cycles previews in
  under ten seconds on the CPU. The first hoe (a screed board) read as a bench in the renders and was
  redone as a square scoop.
- Blender 5.2 gives every new material and world a node tree; `use_nodes` is deprecated (removed in
  6.0), so the script doesn't set it.
- The owner chose the controls from options ([[0012-controls]]); the rectangle's facing edge moves.
  Left Ctrl left out of the defaults because it is crouch. Hand positions wait for the owner's
  screenshot from the first test.

Fourth session (the plugin):
- Decompiled `Humanoid.EquipItem`: tools empty both hands, so the off-hand probe needs a patch
  ([[0013-off-hand-through-a-patch]]). Read the game's default keys; `T`, `G`, `Left Shift` were
  taken, so [[0012-controls]] got new defaults, plus a pin key.
- Read the game's prefabs with UnityPy: the hoe's model sits under `attach/visual` (handle along Z,
  hand at z = -0.51), the torch's under `attach` (rod along +Z). The model placement defaults come
  from that; the owner tunes the rest from a screenshot.
- Built the plugin (Jotunn 2.30.2, BepInEx 5.4.21 references, the game publicized into `obj/`), no
  warnings. Deployed to the `test` instance's `RcinelLevel-dev/`.
- Claude copied Jotunn 2.30.2 from Thunderstore into the instance, not knowing the owner had just
  installed the same version through LaunchHeim; the files were identical and LaunchHeim's record is
  intact, but the "folder exists" check only printed a warning instead of stopping. Check, then stop.
- Gotchas in [[valheim-modding]]: netstandard 2.1 in Unity 6's image module, JotunnLib's props writing
  into the game folder, MSBuild metadata inside property functions.

Fifth session (first test feedback):
- Owner's test: shapes didn't cycle, frame too small, whole-frame levelling unwanted, jagged edges.
- Causes: `KeyCode.Y` is a US position (Z on QWERTZ); overlapping tiles moved vertices twice because
  `m_heights` is rebuilt a frame later ([[terrain-and-multiplayer]]).
- Fixes: layout-aware letter keys; tiles partition the area; the hoe levels a brush inside the frame;
  pinning fixes the target; frame limit 64 by default, up to 128, with a per-heightmap measurement
  ([[0014-hoe-levels-a-brush-inside-the-frame]]). The owner's saved config still said 16; Claude set
  it to 64 in the test instance, since all other values there were defaults.

Sixth session (third round of feedback):
- Hoe head straight on the haft like a shovel ([[0011-model-designs]]); icons rendered from the models,
  diagonal with a dark rim ([[0017-icons-rendered-from-the-models]]); the item SVGs are gone.
- The hoe only raises, priced at Raise ground's stone per m³ ([[0015-hoe-only-fills-and-costs-stone]]);
  the pickaxe gets a depth lock that keeps it inside the frame and above the target
  ([[0016-pickaxe-depth-lock]]).

  times a second.

  held the old defaults for both, so Claude set the new ones there.
- Next test: the end-over-end turn pointed the hoe backwards; turned about the handle instead,
  (90, 0, 0). A stroke on ground within 0.25 m above the target no longer says "nothing lies below".
  Lesson: "upside down" for a tool in the hand needs a screenshot before guessing the axis.
- Owner's test: the hoe now sits right in the hand (screenshot). Asked for a red warning on ground
  that can't reach the target ([[0018-red-overlay-for-unreachable-ground]]) and a free depth of
